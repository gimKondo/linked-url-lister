# リサーチ: URL正規化の強化

## 1. GoでのURL正規化ベストプラクティス

### 決定
Go標準ライブラリの`net/url`パッケージと`path`パッケージを組み合わせて使用する。

### 根拠
- `net/url.URL`構造体は`RawQuery`と`Fragment`フィールドを持ち、これらを空にすることでクエリパラメータとフラグメントを除去できる
- `path.Clean`関数は連続スラッシュの正規化とドットセグメントの解決を行う
- 外部依存なしで憲法の「シンプルさ優先」原則に準拠

### 検討した代替案
- **purell/purell**: URL正規化専用ライブラリだが、外部依存を増やすため却下
- **手動の正規表現処理**: エラーが発生しやすく、標準ライブラリで十分対応可能なため却下

---

## 2. クエリパラメータ除去の実装方法

### 決定
`url.URL`構造体の`RawQuery`フィールドを空文字列に設定する。

### 根拠
- シンプルで直接的な方法
- `url.URL.String()`メソッドは`RawQuery`が空の場合、`?`を出力しない
- パース済みのURLオブジェクトを直接操作できる

### 実装パターン
```go
resolved.RawQuery = ""  // クエリパラメータを除去
```

### 検討した代替案
- **文字列操作**: `strings.Split(url, "?")`で分割する方法は、URLのパース状態を考慮しないため却下
- **正規表現**: 過剰で保守性が低いため却下

---

## 3. トレイリングスラッシュ統一の実装方法

### 決定
`strings.TrimSuffix`でトレイリングスラッシュを除去し、ルートパス`/`は例外として保持する。

### 根拠
- ルートパス`/`はスラッシュ1つが正しい形式
- それ以外のパスはスラッシュなしに統一することで一貫性を保つ
- `path.Clean`はトレイリングスラッシュを保持するため、追加の処理が必要

### 実装パターン
```go
if resolved.Path != "/" {
    resolved.Path = strings.TrimSuffix(resolved.Path, "/")
}
```

### 検討した代替案
- **トレイリングスラッシュありに統一**: 多くのURLがスラッシュなしで参照されるため、除去する方向に決定
- **ファイル拡張子判定**: `.html`などの拡張子がある場合はスラッシュを追加しない必要があるが、TrimSuffixなら自然に対応できる

---

## 4. パス正規化（連続スラッシュ、ドットセグメント）

### 決定
`path.Clean`関数を使用してパスを正規化する。

### 根拠
- `path.Clean`は以下を自動的に処理:
  - 連続するスラッシュを単一スラッシュに変換
  - ドットセグメント（`.`、`..`）を解決
  - 空パスを`.`に変換（ただし絶対パスでは`/`）
- 標準ライブラリで完結し、追加の依存関係不要

### 実装パターン
```go
resolved.Path = path.Clean(resolved.Path)
```

### 注意点
- `path.Clean`は空パスを`.`に変換するが、URLでは`/`が適切なため、後処理が必要
- `path.Clean`は`//`から始まるパスを`/`に変換しない（ネットワークパス扱い）が、HTTP URLでは問題にならない

### 検討した代替案
- **regexp**: 正規表現で`//+`を`/`に置換する方法はシンプルだが、ドットセグメント解決が別途必要になるため却下
- **filepath.Clean**: OSに依存するパス区切り文字を使用するためURLには不適切

---

## 5. 空パスの処理

### 決定
空パスは`/`に正規化する。

### 根拠
- `https://example.com`と`https://example.com/`は同一リソースを指す
- HTTP仕様上、パスなしのURLはルートパス`/`と等価
- `path.Clean("")`は`.`を返すため、明示的に`/`に変換する必要がある

### 実装パターン
```go
if resolved.Path == "" || resolved.Path == "." {
    resolved.Path = "/"
}
```

---

## 6. 処理順序

### 決定
以下の順序で処理を行う:

1. 相対URLを絶対URLに解決（既存処理）
2. フラグメント除去（既存処理）
3. クエリパラメータ除去（新規）
4. パス正規化: `path.Clean`（新規）
5. 空パスを`/`に変換（新規）
6. トレイリングスラッシュ除去（新規）

### 根拠
- `path.Clean`が先に実行されることで、連続スラッシュやドットセグメントが解決される
- その後にトレイリングスラッシュを除去することで、一貫した結果が得られる
- 空パスの変換はトレイリングスラッシュ除去前に行う必要がある（`/`が誤って除去されないように）

---

## 7. 既存コードへの影響

### 現在の実装（internal/filter/url.go）
```go
func NormalizeURL(baseURL *url.URL, href string) (*url.URL, error) {
    parsed, err := url.Parse(href)
    if err != nil {
        return nil, err
    }
    resolved := baseURL.ResolveReference(parsed)
    resolved.Fragment = ""
    return resolved, nil
}
```

### 変更点
- クエリパラメータ除去: `resolved.RawQuery = ""`
- パス正規化: `resolved.Path = path.Clean(resolved.Path)`
- 空パス処理: `if`文で`/`に変換
- トレイリングスラッシュ除去: `strings.TrimSuffix`

### 影響範囲
- `NormalizeURL`を呼び出す箇所（`internal/crawler/crawler.go`の`addLinksToQueue`）
- 訪問済みチェックは正規化後のURLで行われるため、変更なしで動作
- 出力にも正規化後のURLが使用されるため、期待通りの結果になる
